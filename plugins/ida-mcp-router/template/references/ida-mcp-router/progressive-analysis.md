# IDA MCP progressive analysis

本文件只在任务范围较大、需要规划逆向分析路径时读取。目标是把分析过程做成渐进式披露：先定位和筛选，再精读和验证。

## 基本流程

1. **定位**：用名称、字符串、常量、xref、导入符号找到候选。
2. **筛选**：高风险搜索交给子 agent，最多返回 10 个候选。
3. **排序**：主会话按证据强度选择 1-3 个地址。
4. **精读**：主会话对单函数 `decompile`，必要时局部 `disasm`。
5. **验证**：用 `get_*`、`read_struct`、小范围 `xrefs_to` 确认关键判断。
6. **记录**：写入分析笔记，只保留关键地址、字段、条件、调用和结论。

## 多范围任务默认策略

- 如果用户给出多个函数范围、多个候选地址或多个相同 offset 搜索目标，默认交给子 agent 串行筛选。
- 主会话不要对多个范围并发发起 `insn_query` / `search_text` / decompile；只精读子 agent 推荐的 1-3 个地址。
- 子 agent 必须报告每个范围是否完整扫描、是否分页、是否有工具失败或跳过。
- 主会话最终报告只写已验证证据，不把未完整扫描的候选当作排除结论。

## 场景：寻找完整校验点

1. 找构造/注册函数写入了哪些字段和容器。
2. 查这些字段或容器的 xref，默认子 agent 筛选。
3. 按“读取字段 + 条件判断 + 错误路径/返回码 + 外部输入比较”排序。
4. 主会话精读最相关函数。
5. 验证是否存在真实校验，而不是仅复制、缓存、释放或日志路径。

## 场景：判断函数真实语义

1. 先看输入、输出、返回值使用者。
2. 再看关键字段偏移、内存分配、容器操作、外部 API。
3. 不急于命名；先写“更像 X，不像 Y，因为 ...”。
4. 查调用者/被调者验证语义。
5. 只有证据稳定后再考虑 `rename` 或注释。

## 分析笔记格式

```text
地址/函数：<addr/name>
观察：<关键字符串、字段、调用、条件>
结论：<当前判断>
置信度：高/中/低
下一步：<需要继续验证的位置>
```

不要把完整伪代码、完整汇编、大段 CFG 或完整 xref 列表复制进笔记。
